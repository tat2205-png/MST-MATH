# RFC-0001 — MST Pedagogical Intelligence Boundary

Status: EXPERIMENTAL
Decision: CONTRACT LAB ONLY
Authority: user-approved architecture, subordinate to MST-MATH canonical contracts

## 1. Problem

MST-MATH needs richer pedagogical analysis and, later, exercise transformation/generation. The main engineering risk is not lack of model capability; it is semantic corruption caused by multiple parsers, model outputs, or validators acting as competing truths.

## 2. Core decision

**One canonical truth:** MST Canonical IR.

External systems are replaceable adapters. They may return evidence and candidates, but they never write canonical semantics directly.

```text
SOURCE
  -> MST INPUT AUTHORITY
  -> CANONICAL SOURCE IR
       -> native PASS: continue
       -> recovery required: ExternalAdapter -> ParseCandidate
  -> deterministic reconciliation
       -> canonicalize only after MST validation
       -> conflict => REVIEW_REQUIRED
```

## 3. V1 boundary

V1 implements contracts and deterministic policy only. It deliberately excludes model/provider code, parser packages, generator code, UI, persistence migration, and production wiring.

This prevents the experiment from becoming a hidden feature expansion while Core is under the no-improvement freeze.

## 4. Anti-corruption layer

Third-party schemas must terminate at an adapter boundary.

```text
Third-party output
      -> adapter/anti-corruption layer
      -> MST ParseCandidate / AnalysisCandidate / GenerationRecord
      -> MST deterministic validation
```

No downstream MST component may depend on a Marker/MinerU/MathOCR/Pix2Text/LLM-native schema.

## 5. Authority hierarchy

For this lab:

1. current explicit user instruction;
2. MST canonical architecture/contracts;
3. deterministic verification/QA;
4. Human Authority for mathematical, pedagogical, and visual judgment;
5. lab policy;
6. third-party/model proposal.

A model output is never mathematical truth or curriculum truth.

## 6. Status vocabulary

Use only project-standard states for gates:

- `PASS`
- `FAIL`
- `BLOCKED`
- `NOT_TESTED`
- `REVIEW_REQUIRED`

Parsing evidence additionally uses descriptive evidence states:

- `EXACT`
- `VALIDATED`
- `RECOVERED`
- `AMBIGUOUS`
- `CONFLICT`

These are not release-gate PASS/FAIL states.

## 7. No fake confidence

Numeric confidence values are forbidden in V1 contracts unless a future RFC documents calibration data and acceptance thresholds. Conflict is represented explicitly, not hidden behind a score such as `0.93`.

## 8. PedagogySpec design

Bloom/DOK are secondary metadata, not the semantic core. The contract centers on:

- learning objectives;
- mathematical concepts;
- prerequisites;
- student actions;
- reasoning demands;
- representations;
- misconceptions, including `KNOWN` vs `HYPOTHESIZED`;
- evidence of learning;
- difficulty factors;
- scaffolding policy;
- answer-exposure policy;
- curriculum alignment;
- provenance.

## 9. Generation genealogy

Any future generated/derived question must record:

- parent question ID;
- transformation type;
- generator/version;
- prompt version;
- model version when applicable;
- math, pedagogy, and curriculum validation states;
- teacher review state.

This enables targeted invalidation when a generator/prompt/model version is later found defective.

## 10. Recovery policy

Do not run every parser in parallel by default.

```text
native parse
  -> PASS and no conflict: accept native evidence
  -> recoverable failure: request one configured recovery adapter
  -> native/recovery disagreement: REVIEW_REQUIRED
  -> unsupported source: UNSUPPORTED/REVIEW_REQUIRED at owning boundary
  -> technical failure: ERROR at owning boundary
```

No majority voting across parsers.

## 11. Dependency isolation

Future external engines must be isolated behind adapters and preferably separate environments/processes. The Core dependency graph must not import third-party parser/model packages directly.

Before approval, each component requires a ledger entry covering code license, model-weight license, redistribution, commercial-use constraints, attribution, version pinning, runtime footprint, network behavior, and removal strategy.

## 12. Security requirements

Future document workers must treat input as untrusted and enforce bounded temporary storage, timeouts, file/page/recursion limits, no macro execution, least-privilege filesystem access, and network denial unless explicitly required.

## 13. Review scaling

Teacher Authority remains final, but future review must be risk-based. Routine deterministic transformations may be batch-reviewed; ambiguous, open-ended, modeling, geometry, or conflict cases require stronger review.

V1 does not automate approval.

## 14. Promotion criteria

Promotion requires all of the following:

1. Core working baseline is certified (`FUNCTIONAL/STABLE`).
2. Lab contracts are reviewed and versioned.
3. Golden corpus covers representative GDPT2018/KNTT question types.
4. Provenance completeness gate passes.
5. Conflict routing is fail-closed.
6. No direct third-party schema leaks into Core.
7. Dependency and license ledger is approved.
8. Performance/resource benchmark is recorded on Windows PC.
9. Model/prompt drift tests exist where AI is introduced.
10. Independent technical review and Human Authority approval are complete.

Until then the lab remains non-production and has no official MST module number.
